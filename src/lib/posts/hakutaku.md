改了一张背景图，玩家已经下载过的语音和音乐怎么办？播放一段长音频时，要先把整包打开吗？Hakutaku v1 把发行清单和实际数据分开，这两个问题就可以分别处理。引擎或启动器仍负责下载，媒体也由引擎解码和播放。

这篇记录的是 **v1 格式**。下面的实现和实测来自 `v0.1.7`，测试提交为 `ce8fe3c`。

## 文件结构

打开一个发行目录，能看到一份签过名的 `game.haku`，旁边是一批 `.taku` 文件。前者描述这次发行有哪些资源，后者装的是实际数据。

`game.haku` 里有固定头、加密压缩目录、资源路径索引、文件到数据块的映射页、块复用信息、Required/Deferred 段清单，以及单调递增的 `release_sequence`。

每个 `.taku` 文件的名字来自整段内容的 BLAKE3 标识。写出来以后，这个段就不再改了。两次发行用到同一段时可以共用它。安装器拿到认证过的清单，可以先装 Required 段，等需要时再取 Deferred 段。什么时候下载、失败后怎么重试，仍由引擎或启动器决定。

## 认证与加密

| 用途                         | 固定算法        |
| ---------------------------- | --------------- |
| 目录、页面、资源块加密认证   | AES-256-GCM     |
| 发行快照签名                 | Ed25519         |
| 内容寻址、密钥派生、签名承诺 | BLAKE3          |
| 可压缩资源                   | 独立 zstd frame |
| 已压缩媒体                   | RAW 加密块      |

打开包时先验签，再解密目录。目录里有元数据页的摘要，元数据页又记着资源块密文的摘要。这样读到具体某块时，可以沿着目录和页一路核对到发行者签过名的快照。已经通过认证的明文可以留在有容量限制的缓存里，下次再读就直接用。

旧版本的签名也可能是有效的。要防止回滚，启动器需要记住自己接受过的最高 `release_sequence`，下次打开时把它当作最低允许值。序列号低于这个值的快照会被拒绝。

## 分块与缓存

一段脚本可能经常回来查，一句语音通常说完就过了。背景图和长音频也有各自的读法。参考打包器把它们分为四类，运行时对 Hot 积极保留缓存，Normal 到第二次访问才缓存，Transient 通常读完就丢，Streaming 按顺序读。

| 访问类型  | 典型资源             | 参考分块策略                                           |
| --------- | -------------------- | ------------------------------------------------------ |
| Hot       | 小脚本、UI、小配置   | 单块，最大 32 KiB                                      |
| Normal    | 背景、立绘、普通资源 | FastCDC 32–512 KiB，平均约 128 KiB；超大资源固定 1 MiB |
| Transient | 短语音、短音效       | 固定 256 KiB                                           |
| Streaming | BGM、长音频、视频    | 固定 256 KiB                                           |

参考实现先看扩展名，再看大小。一段不足 32 KiB 的 `.opus` 仍然是语音，不会因为文件小就按 Hot 处理。WebP、PNG、JPEG、AVIF、Opus、MP3、Ogg、FLAC 和常见视频容器本身已经压过，再套一层 zstd 通常省不了多少。所以它们直接写成 RAW 加密块。

Required 和 Deferred 分开写，每种 AccessClass 也各用自己的段写入流。这样后面做增量时，短语音、流媒体和经常访问的小文件少一些互相牵连。

## 连续读取

临时读一段数据，直接用 `Asset::read_at` 就够了。播放音频或视频时，解码器往往会接着读，还会偶尔往回跳一点。这样的调用可以一直用同一个 `AssetCursor`，对应标准 `Read + Seek`，或者用按偏移量读取的 `AssetReadSession`。两者都能复用下面这些东西。

- 当前打开的数据段句柄；
- 密文与解压明文缓冲区；
- 已准备的密码学状态；
- 当前与前一个 Streaming 块。

为什么还要留前一块？假设解码器从 A 读到 B，又跳回 A。第一次读 A 和 B 都得认证，最后一次可以直接从游标拿到之前读好的 A。

要提前读一段，可以把同步的 `prefetch_range` 调用放进引擎自己的任务池，在消费前先把指定范围认证好。默认给元数据页、明文和预取各留 2 MiB、64 MiB 和 2 MiB，再保留 16 个闲置段句柄和 256 条 Normal 首次访问记录。设备内存紧张时，预算可以调低，可重建的缓存也可以全部关闭。

## 机械硬盘测试

为了看看首次读取和回头再读能差多少，当时用 Kēne 0.8.1 在 Windows 的机械硬盘上跑了一组测试。提交是 `4df5e17804d0`，用的是本文这一套 Hakutaku 后端。

| 测试 | 首次访问 | 重复访问 |
| --- | ---: | ---: |
| Hot | 102.2 MiB/s | 849.8 MiB/s |
| Normal | 18.3 MiB/s | 1,023.1 MiB/s |
| 512 × 4 KiB 随机 seek | 405 IOPS | 5,151 IOPS |

首次访问选了互不重叠的范围，系统和硬盘缓存却没有清空。所以第二次读快了多少，里面同时有系统、硬盘和 Hakutaku 缓存的影响。这组数据也没有对比不同的缓存算法。

## 增量构建

修改一个文件后重新打包，旧版本里仍然有效的加密块可以继续用。同一兼容类别中的相同内容也能去重。普通增量构建还是会重读源文件，重新分块和计算哈希，确认哪些块真的可以复用。

本地反复打包时，可以用 `--dev-cache` 少做一部分工作。它记下逻辑路径、大小、修改时间、平台能提供的文件身份、已认证的分块元数据，以及所属项目和发行序列。缓存损坏、过期或对不上，就忽略这份记录。

开发缓存命中时会跳过源文件的逐字节复核。正式发行仍走普通构建或 `--full`，两者都重读源文件、验证暂存的成品，再逐字节比对资源。需要清掉历史增量里已经无人引用的数据时，用 `--full` 重写活跃资源。

## 密钥与安全范围

打包人和玩家手中的材料权限不同。Publisher Identity 有内容根密钥和 Ed25519 私钥，可以签新发行。Runtime Key Material 带的是内容根密钥和公开验证密钥，运行时靠它读取内容并验证签名。

完整身份文件只在打包时加载。读取、列表、提取和验证工具都用 Runtime Key Material。打包器和 GUI 会检查文件魔数，因此把密钥文件改个名字也不会作为游戏资源导入。打包前还会检查输入与输出目录之间的嵌套关系。

离线客户端需要解密，对客户端有足够分析能力的人也有机会提取资源。签名解决的是发行者身份和内容完整性。缺少 Ed25519 私钥，就无法签出一份能通过认证的新快照。替换已被签名承诺的数据块，同样过不了校验。

## v0.1.7 性能测试

这组数据是在 2026-08-22 测的。机器是 Apple M5 Pro，24 GB 内存，macOS 27.0。Hakutaku `v0.1.7`（`ce8fe3c`）用 Rust release/bench profile 构建，只跑了一次。文件系统缓存已经预热，数字适合看同条件下的差异，目标设备冷启动时还要另测。

### 32 MiB 流式资源

这一项用程序生成了可复现的 32 MiB 数据，模拟像 MP4 这样基本压不动的资源。短距离 seek 命中内存时约 2,333 万次/秒，主要测到的是相邻块已经认证之后，数据从内存复制出来的速度。随机 4 KiB 读取的 IOPS 另列在下表。

| 指标                     |             实测 |
| ------------------------ | ---------------: |
| 完整打包及暂存验证       |       112.077 ms |
| 签名快照打开             |         0.056 ms |
| 128 KiB 顺序读取         |    1,635.8 MiB/s |
| 256 KiB 顺序读取         |    1,644.3 MiB/s |
| 10,000 次随机 4 KiB 读取 |       6,578 IOPS |
| 数据块数量               |              128 |
| 加密段体积               | 33,560,576 bytes |

### 资源目录

路径会在已经认证过的内存目录里找。表里「路径查找后端读取」为零，因为这一步还没有打开对应的资源数据。

| 指标                 | 10,000 assets | 100,000 assets |
| -------------------- | ------------: | -------------: |
| 首次严格打包         |    572.436 ms |   6,525.188 ms |
| 未修改严格增量构建   |    341.594 ms |   4,973.689 ms |
| 开发缓存命中         |    160.139 ms |   2,031.202 ms |
| 开发缓存相对严格增量 |      快 53.1% |       快 59.2% |
| 进程内首次打开       |      1.767 ms |      17.169 ms |
| 1,000 次随机路径查找 |      0.395 ms |       0.523 ms |
| 路径查找后端读取     |       0 bytes |        0 bytes |

### 读取放大

读取放大看的是实际从后端读了多少字节，相对请求的资源有多大。背景、立绘、BGM 和视频的测试结果接近 `1×`。24 KiB 的短语音比例更高，因为 4 KiB 段头、元数据页和块认证的固定开销，在小文件里占得更多。

| 读取场景                    |     耗时 | Read amplification |
| --------------------------- | -------: | -----------------: |
| 512 KiB 背景完整读取        | 0.366 ms |             1.022× |
| 512 KiB 立绘完整读取        | 0.347 ms |             1.022× |
| 24 KiB 代表语音             | 0.050 ms |             1.307× |
| 4 MiB BGM 顺序读取并短 seek | 2.811 ms |             1.126× |
| 8 MiB 视频顺序读取并短 seek | 5.369 ms |             1.063× |

### 去重

把同一份 4 MiB 文件登记四次，逻辑上有 16 MiB。打包器实际只写了 26 个新块，其余 78 个引用指向已有的块。加密段最后是 4,198,816 bytes，约 4.004 MiB，比逻辑内容少约 75%。
